## Project description

The BeXT bank transcation categorization tool
A tool to upload csv bank extracts and categorize all transactions based on keyword matching.

## Requirements

- **User management** — Login with username & password. Multi-user with **real data isolation** (every entity is scoped to a user; a user never sees another user's data). **No public self-registration** — accounts are created by an **admin**. A default admin (`admin`/`admin`) is seeded on first boot with a change-password nudge until the default password is replaced.
  1. **Admin role** (`is_admin`) — admins get extra pages: **user management** (create/delete users, reset passwords, grant/revoke admin) and **application default settings**. Guards: an admin cannot delete their own account, and the last admin cannot be deleted or demoted.
  2. **Application defaults** (a singleton) — default currency and global fuzzy distance that **seed a new user's own settings at creation time** (a snapshot; later changes to app defaults do not retroactively affect existing users).
  3. User settings — a page of **named sections with a rail beside them** (Preferences, Appearance, Password, Exchange rates, Backups, Danger zone), rather than one scroll of everything; the rail says which section you are in and jumps to any of them, and the sections themselves sit in **two columns from 1280px** so the page uses the window like every other page. It scrolls elements rather than linking to `#ids`, because the router itself lives in `location.hash` and an anchor would navigate the app away. Settings holds: default currency, a **global fuzzy-match distance** for classification (0 = exact substring match, 1 = Levenshtein distance 1, etc.; overridable per keyword), a **light/dark theme** preference (persisted per user; applied via semantic color tokens in `client/src/app.css` driven by `data-theme` on `<html>`), and **transactions per page** (default 100; the transaction list's page size and its "load more" step — no upper limit, with `0` = *All transactions* offered behind a performance warning). The list's own footer offers 100/200/500/All or any number and saves the change back to this setting.
  4. **Backups** — a `VACUUM INTO` snapshot of the whole database file (never a `cp`, which silently copies a stale pre-WAL state). Taken automatically before anything that destroys transactions (upload confirm, upload rollback, clear-all-transactions, account delete, admin user delete) and on demand from the settings page; the newest 5 survive in `server/data/backups` (`BEXT_BACKUP_DIR` moves them). A snapshot holds every user's data, so the API lists names/sizes/reasons and never serves the bytes. Restore is CLI-only (`npm run db:restore <file>`) — it integrity-checks the snapshot, prints its row counts, snapshots the current database, and refuses to run while a `-wal` says the server still holds the file.
  5. **Clear all transactions** — a *danger zone* action on the user settings page: wipes the signed-in user's own transactions, splits, hashtags and upload archive, while keeping institutions, accounts, CSV templates, OFX settings, categories, keywords and FX rates. Per-user (never another user's data), so it lives under `/api/settings`, not `/api/admin`; requires an explicit confirmation and warns up front how many locked or split transactions would be destroyed.
- **Home** — a **way in, not a dashboard**: one tile per page, each carrying a single cheap figure (transactions and how many are uncategorized, the last import, accounts and institutions) rather than a report. The month's numbers and the charts live on Graphs, which does them properly one click away; repeating a worse version here only made the page slow to open. Above the tiles, an *attention* strip appears **only when something is waiting** — uncategorized rows, accounts with no import template. It reads four small endpoints and no report query. On first run the tiles give way to the three getting-started steps.
- **Institution and Account** — Users register institutions, then accounts under them. The page is a **ledger**: one sortable row per account, the institution printed once per group (statement-style, repeated only for assistive tech), plus a summary strip (transactions, coverage, currencies, holders, accounts still missing a template). Sorting reorders the *groups* by their leading row and the rows inside them, so an institution stays one block however the table is sorted; institutions with no accounts keep a row of their own. Per-account figures (`txCount`, `firstDate`, `lastDate`, `uploadCount`, `lastUploadAt`, `hasOfx`) come from `GET /accounts?stats=1` — opt-in, because the other pages read `/accounts` only for names and should not pay for a scan of the transactions table to fill a dropdown. Split children are excluded from `txCount`, so a split transaction counts once.
  1. Accounts have a **mandatory currency**.
  2. Accounts have an **account holder** — a free-text name of the person the account belongs to (default = the user, but could be spouse/child/etc.). Free text, not a managed entity.
- **Bank extracts upload** — Users define a reusable **CSV template** per account (see the CSV template model in Decisions).
  - CSVs may have 1+ **description** columns → merged into one `description`.
  - CSVs may have 1+ **amount** columns → summed into one signed `amount` (e.g. Revolut `Amount` + `Fee`).
  - CSVs may have multiple **date** columns → the template picks exactly one to map to the transaction `date` (default: the transaction date, not the posting/completed date).
  - CSVs may carry the **currency** in a column → mapped to `currency`; if absent, falls back to the account currency.
  - **Row filters** (e.g. `State = COMPLETED`) are saved on the template and applied automatically on every upload; individual rows can still be excluded in the preview.
  - **Dedup:** same `date + description + amount`. Two identical rows _within the same file_ are two distinct transactions; an identical row appearing in a _later upload_ is a duplicate and is dropped.
  - The page is **setup on the left, work on the right**: a sticky rail holds the file (click or drop), the template's state and the Preview button, while the mapping table and the preview take the window. The account is picked from **a box per account, grouped under its institution** — each showing its currency, holder and whether it has a CSV template or imports OFX — and **a statement can be dropped straight onto an account**, which selects it and loads the file in one move. The archive is a table (file · account · when · imported · still there · what a rollback would destroy).
  - **The template editor maps by showing the data.** Choosing a file reads its columns immediately (using the saved template's encoding/delimiter/header row as the first guess), and every column becomes a row carrying *its first values from the file* with its roles as chips: date, description, amount, currency, FX amount, FX currency. Date and the currency roles hold one column and move when clicked elsewhere; description and amount take several. **Map it from this file** throws the saved mapping away and re-guesses from the file — the auto-guess on detect only ever fills fields left empty, which is no use when the saved mapping belongs to another bank's export. A column the mapping names but the file lacks is marked *not in this file*, and **a row filter pointing at a missing column is called out** — it silently excludes every row, and "22 filtered" in the preview never said why.
  - Classification runs on upload with a **preview-and-confirm** step before persisting.
  - The template is **saved and assigned to the account**, and a new account can **copy the template** from an existing account.
  - Keep an **upload archive/history** page listing past uploads.
- **OFX / QFX upload** — where a bank offers OFX, it is the better path: the file is self-describing, so it needs **no template at all** (no delimiter, decimal separator, date format or column mapping). Format is detected from file *content*, not the extension, so `.ofx`, `.qfx` and mislabeled files all work. Bank (`STMTRS`) and credit-card (`CCSTMTRS`) statements only. Everything after parsing — preview-and-confirm, classification, business-flag defaults, the archive and rollback — is the same pipeline as CSV. See the OFX decisions below.
- **Categories** — Customized categories and optional subcategories, assigned to transactions. The page is a **board**: a card per category flowing into up to four columns, each carrying what the category is worth — its transactions, its net and how many keywords point at it — with the same figures per subcategory and a share bar in the category's own colour. `GET /categories` returns `txCount`, `amountCents`, `unconvertedCount`, `currency` and `keywordCount` per category (and the first three per subcategory). **Amounts are FX-converted before they are summed**, exactly as the reports do: a category holding PLN, EUR and BRL rows would otherwise report the sum of three currencies, which is not a number. Rows no rate reaches are counted in `unconvertedCount` and marked with an asterisk rather than silently mixed in. Split containers are skipped so a split counts once through its children; hidden categories *are* counted here, since this is the page where you decide whether to keep them.
  - Download / upload categories & subcategories (round-trips the seed JSON shape).
  - Seeded from the default list on first run.
  - Subcategories are optional.
  - Expense vs. income is **not** stored on the category — it is derived from the transaction amount sign (see Decisions).
  - A category (and a transaction/split) can be flagged **business vs. personal** (see Decisions).
- **Keywords** — Keywords connected to a category and (optionally) a subcategory. The list is a **yield table**: every rule shows `matchCount` — how many transactions it currently owns — with a bar in its category's colour, sortable by keyword, category or matches (matches first by default), and rules matching nothing carry a *no matches* chip. Filter chips narrow to those and to rules with their own distance. **Clicking a rule opens a side panel** (closed until then, Escape or × to close) listing the transactions that rule classified, read from `/transactions?keywordIds=`, so the panel shows exactly the rows the count counts. `matchCount` counts rows *attributed* to the rule, not rows it would match — a longer keyword that outranks it holds those instead, which is what *longest keyword wins* looks like from this page.
  - Download / upload keywords.
  - A keyword may carry a **per-keyword distance override**; otherwise the user's global distance applies.
  - Classification is **deterministic and re-runnable**: running twice on the same data yields the same result, and re-classifying after rule changes is supported. **Manual categorizations are locked** and never overwritten by a re-run. Conflict resolution: **longest matching keyword wins**.
- **AI categorization** — an *AI review* page (`/ai`), the transaction list turned into a review queue: an AI engine reads the merchants you have not categorized, looks each one up **on the web**, and proposes a **keyword → category/subcategory rule** you accept or reject. The unit is the **merchant, not the row** — descriptions are normalized into a `groupKey` (the engine's own tokenizer, minus numbers and single letters, so `ZABKA Z7412 KRAKOW` and `ZABKA Z8155 KRAKOW` are one merchant), so one lookup answers every repeat and "analyze 25" means 25 merchants. Groups are offered biggest-first, so a capped run buys the most classification.
  1. **Engines** — Claude, OpenAI, Google Gemini (your key *or* a free one the server supplies) and DeepSeek, each a thin adapter returning `{text, sources}` from one prompt contract. JSON comes from the **prompt**, not from a provider's schema mode, and one tolerant parser reads it back: the providers constrain JSON differently and two of them have rules about combining a schema with server-side web search, so a single contract never 400s on a feature interaction. A provider declares whether it **can** search the web — DeepSeek's API cannot, so the switch is disabled for it and its proposals are logged as ungrounded rather than silently downgraded.
  2. **Keys are per user, stored encrypted** (AES-256-GCM, `server/src/ai/crypto.js`) — a plaintext column would be readable in every backup snapshot, and a snapshot holds every user's data. The API never serves a key back, only its last four characters. The encryption key comes from `BEXT_AI_KEY_SECRET`, else a random `server/data/.ai-key` (0600) generated on first use. The free Gemini engine reads `BEXT_GEMINI_FREE_KEY` from the **server** and is simply not offered when it is unset — a key committed to the repository would be a published secret.
  3. **Run once per engine, never twice.** Every proposal is logged under an `engineKey` = `provider:model`, with a unique index on `(userId, engineKey, groupKey)`: an engine gets one answer per merchant **whether you accepted it or not**, enforced by the database rather than by a query the runner might forget. Changing provider *or* model makes those merchants eligible again — the deliberate escape hatch for a second opinion. `ai_proposal_transactions` logs which transactions each proposal covered, so "was this row analyzed, and what was proposed for it" has an answer that does not depend on re-deriving the group key. A **provider failure logs nothing** for that merchant, so a later run tries it again.
  4. **A run is a background job with a database row** (`ai_runs`), not an HTTP request the page waits on: a web-searching engine spends tens of seconds per merchant, so the page creates the run and polls it, a reload picks it back up, and *stop* lets the merchant in flight finish (it is already paid for) without starting another. Three merchants run at a time.
  5. **Accepting is editable, and means one of two things.** The keyword and the category are both editable in the row before it lands — the engine is a first draft, not a verdict. *Accept rule* creates the keyword and runs the normal recompute, so it covers this merchant now and next month (and the covered **manual** rows too, which a recompute never touches); *just these* categorizes only the transactions the proposal covered, locking the imported ones exactly as a manual categorization does. An engine that cannot place a merchant says so: the proposal is logged **without a category** (so it is not re-analyzed) and the page asks you to pick one.
  6. A category the engine invented, or one belonging to another user, is dropped rather than stored — the prompt is given the id list and must choose from it.
- **Transaction list** — a **ledger**: one line per transaction, laid out as a grid (date · description · account · category · tags · amount · actions) so amounts align in a single column instead of stacking onto a second line per row. The description is the only elastic track — it takes whatever the fixed ones leave. **Account, category and tags can each be switched off** from a *Columns* control in the list header, which hands their width to the description; the choice is per browser (`localStorage`, key `bext.transactions.columns`), not a user setting, since it is a view preference rather than data. Below 1024px the three optional columns drop out whatever the preference says, and the toggles say so. Comprehensive, filterable list (by category, subcategory, holder, account, **currency** (multi-select, on the transaction's own currency — one account can hold several), business/personal, hashtag, date range, expense/income, **free text over the description** (`?q=`, every whitespace-separated term must appear; LIKE wildcards are literal; ASCII-case-insensitive, not diacritic-folding), and **the keyword that categorized the row** (`?keywordIds=`, with `0` = matched by none)), sortable by date (newest/oldest) or **description** (case-insensitive, so repeats of one merchant sit together while working through the uncategorized tail).
  - **Period as a set of months:** `?months=YYYY-MM,…` selects individual months (the Explore toggles); it ANDs with the `from`/`to` range. Sorting also offers **by value** (`amount_desc` / `amount_asc`), ranked on |amount| so the biggest movements lead whichever way the money went. Both live in the shared filter/sort layer, so the reports see exactly the same rows as the list.
  - **Grouped view** (`GET /transactions/groups`): the list folds into one line per *description* (case/spacing ignored) or per *merchant* (the AI review's `groupKey`, so branch numbers fold together), each with its count, date span, category (or *mixed*) and FX-converted total, ranked by |total| by default (or count, description, date). Same filters as the list, split containers skipped; a group expands in place (`/groups/members`), and categorizing, selecting or tagging a group acts on all its rows. With *uncategorized* on, this is the queue of what to classify first. Column headers sort the row list too (date, description, account, category, amount — a second click reverses).
  - **Classification progress:** a bar over the list showing how much *money* (in the user's default currency, FX-converted) is still uncategorized under the current filters — the category selection itself is ignored so the bar keeps meaning while filtering for uncategorized. Rows no rate can reach are excluded from the amounts and named in a subtle note under the bar.
  - **Bulk categorize:** the row selection that tags in bulk also categorizes in bulk — pick a category in the selection bar and it lands on every checked row (`POST /transactions/bulk-categorize`), locking the imported ones exactly as a single manual categorization does. The answer for merchants no keyword will ever describe.
  - **Inline keyword creation:** filter for "uncategorized", select a word/phrase in a description, create a keyword + category/subcategory inline; all matching transactions are auto-categorized Selecting the text opens the keyword popover **directly** (the row's + button opens the same one): the phrase stays editable and the category list is already open, led by **suggestions** — the last few picks, then the category/subcategory pairs holding the most transactions (`client/src/lib/recentCategories.js`). Picking a category *is* the commit. Last-used picks are per browser (`localStorage`, `bext.categories.recent`), recorded from every category pick on the page.
  - **Hashtags:** attach one or more free-text hashtags to a transaction to cluster ad-hoc activities (apartment renovation, a specific trip, etc.). A palette of the user's tags sits to the right of the list; a tag is **dragged onto a transaction** to attach it, and rows can be **multi-selected** (checkbox, shift-click range, select-all-loaded) to tag many at once — dropping on any selected row tags the whole selection.
  - **Split transactions:** a transaction can be split into child lines that must sum to the parent amount; each child gets its own category/subcategory/business-flag/hashtags. The parent becomes a container — only the children count in reports.
  - **Hidden categories/subcategories:** categories that are excluded from the list, graphs, and totals by default (e.g. internal transfers between accounts) — a `includeHidden` switch on the transaction list and on both graph pages counts them back in for the periods where one of them really belongs in income − expenses. (Auto-reconciliation of transfer pairs is deferred; for now they are just hidden.)
  - **Manual transactions:** add transactions by hand.
  - **Virtual cash transactions:** a cash spend draws down a **per-currency LIFO cash pool** fed by ATM withdrawals (see Decisions).
- **Exchange rates** — the uploaded `(date,from,to)→rate` table lives on its own **Rates** page (top-level nav), not on Settings: add a rate by hand, import/export the `date,from,to,rate` CSV, filter by currency pair and date range, page through the list (200 at a time), delete a single rate or every rate matching the current filter. Settings keeps a summary card (row count, pairs, date span) linking to the page — a daily table runs to thousands of rows and made Settings unreadable.
- **Budget** (`/budget`, `/budget/setup`) — the months as a household **P&L**, so the average month, the fixed/variable split and the one-offs have an answer. Lines are **named by the user, each of a fixed kind** (`income`, `tax`, `committed`, `fixed`, `periodic`, `variable`, `extraordinary`, `excluded`); the subtotals come from the kinds: **net income** = income + tax, **discretionary income** = net income + committed (the big costs known to come every year — school fees, building administration, flights home — set apart so what is left to live on reads directly), **normal-month result** = discretionary + fixed + periodic + variable (+ unassigned), **net result** = normal month + extraordinary. `excluded` lines (transfers) are shown, never summed.
  1. **Statement** — rows are the lines grouped by kind, each expanding into category → subcategory (or hashtag → category for rows a hashtag routed); columns are the window's months plus **Mean** and **Total**, both over the same months (the complete past months, so total = mean × months) — a period sum reads better in a P&L than a median did. Names are pinned left and Mean/Total right (exact widths, so the sticky offsets meet), so a 24-month window scrolls its months between them. The window is the last 3/6/12/24 **complete** months, the **next** 3/6/12 months, or a calendar year — years run forward to the last month anything reaches (`horizon`: the end of the longest spread, or a future-dated row). The month in progress is a greyed column **kept out of Mean and Total**; **months ahead** are shaded and hold only what is already committed to them (spread slices, future-dated rows), so they stay out of the averages too — except in a window wholly ahead, which averages its committed months and says so. A rail narrows by account, holder and business flag, and sets the display currency (FX-converted; rows no rate reaches are **left out and named**, never mixed in at face value). Six headline figures sit above, in statement order: net income, committed, discretionary income, living costs, normal-month result, net result (with the one-offs and the share of income kept).
  2. **Drill-down** — every figure opens a drawer listing exactly the rows behind it (`GET /budget/rows`, built from the same entries as the statement), with how each row got there (pinned / hashtag / subcategory / category / hidden / uncategorized); a row can be pinned or spread from the drawer.
  3. **Setup** — lines by kind (add, rename, change kind, reorder, delete — deleting un-maps, it never deletes money); each category and subcategory mapped to a line, with its **regularity** over the last 12 complete months beside it (months active, mean, steady or not) and a note when the mapping disagrees with the kind the numbers suggest; the ordered list of **hashtags that route rows** to a line; *start over* re-proposes everything.
  4. **First open proposes a starting set** from the category names (the seed list and its usual renames) and, where names do not place a category, its regularity (→ an "Other …" line of the suggested kind). Only lines that receive something are created, plus *One-offs*. It is a draft; nothing is proposed again unless asked.
  5. Per transaction (edit dialog, or the drawer): a **pin** to any line, and a **spread** over N months (1–120) from the month it was paid. Neither is allowed on a split container — its lines carry them.
- **Transfers** (`/accounts/transfers`, a tab beside Accounts) — money moving between your own accounts, reconciled (`server/src/transfers/reconcile.js`). **Pairing is recomputed from the data on every read, like classification, and only links — it never rewrites a category.** Only decisions are stored (`transfer_decisions`: *confirmed* stands whatever the matcher says, *rejected* is never proposed again).
  1. **Pairs** — a leg in a hidden category (Transfer In/Out) finds its other leg in a different account, opposite sign: the same amount in the same currency within 4 days, or an exchange within 3% after conversion within 2 days; biggest legs first, closest by date, then amount, then id. Automatic when both legs are transfer-ish (hidden or uncategorized); when the other leg is filed as spending or income only *suggested*, and only on the exact same amount — an FX match within 3% against a purchase was a coincidence every time on real data. Pairs across holders (you ↔ a partner) are internal like any other; the P&L's holder filter does not yet turn them into one person's income.
  2. **Off-book accounts** (`offbook_accounts`: name, kind exchange/savings/loan/other, texts that identify their rows — matched like keywords, whole words in order): accounts you own but do not import (a bank's exchange wallet, a broker, a term deposit, a loan). A transfer-ish row naming one is internal, and the account gets a **monthly running balance** (money in − money back, each row at its own date's rate). An exchange wallet is judged against what passed through, not against zero: the rate table is not the bank's rate, and 1.3% drift on 1.7M is "near zero".
  3. **No other side** — hidden-category legs neither paired nor claimed: money that left or entered the household filed as a transfer. Grouped by account, direction and counterparty (the AI review's merchant key); each group can be declared as an off-book account (name, kind and pattern drafted from the group — the longest run of words not on most of that account's rows, so the owner's name printed on every Alior line is skipped), moved to a category (ticked rows, locked), or marked fine (a Health dismissal under its own key, out of the count until its rows change). Uncategorized rows are not asked about here — they are not transfers until someone says so. Health carries one summary finding per state, pointing at the tab.
- **Data health** (`/health`) — checks for the mistakes that quietly bend every total, each one first found by hand: salary filed under Restaurants by a keyword matching the user's own street, a child benefit booked as a ZUS refund by `zus`, ATM cash hidden under Transfers, a bank line shifted by an unquoted delimiter. Four families (`server/src/health/checks.js`):
  1. **Rules** — a keyword whose text also appears in rows of ≥ 2 other categories (≥ 5 rows): shared text (a name, an address, bank boilerplate) that loses there only because longer keywords win. A "broad one-word keyword" check was built and dropped: chains (biedronka, carrefour) have a merchant key per branch address, so it flagged working keywords; the real danger (a first name catching strangers) shows up as Direction anyway.
  2. **Direction** — a category's direction is where most of its *rows* go (money breaks ties): 42 misfiled salaries outweigh years of meals in money and would make Restaurants look like income. Rows going the other way are grouped by what put them there (one keyword, or a hand categorization) and raised once they reach 5% of the category's money or any single row reaches 1,000 in the display currency — small refunds stay quiet. Hidden categories go both ways by design and are skipped.
  3. **Imports** — broken letters (U+FFFD, `ďż˝`, UTF-8 read as a single-byte page), 0.00 rows, impossible rows (unreadable currency, ≥ 10M), and duplicates the dedup missed: same account, date and amount with the same words written differently (identical wording is not a duplicate — the dedup key already counts those occurrence by occurrence).
  4. **Structure** — categories/subcategories with no rows and no keywords; keywords that classify nothing, split into *outranked* (their text appears, a longer keyword wins — a same-words twin is called a duplicate) and *unseen* (their text appears nowhere; some wait for an account not imported yet); categories not on a Budget line.
  - **Every finding shows its evidence, not just a statement**: its rows as a ledger (the keyword's words marked in each description — ranges from `highlightRanges`, on the engine's own token rules — and a long description starting just before the mark), where each row sits now and what put it there. Direction findings add a **strip** of every row in the category on a symmetric-log money axis with the flagged ones drawn over them (a refund sits near zero among the rest; a misfiled salary far off on the other side); shared-text findings show **where the keyword wins today** beside where its text also appears; outranked keywords expand to the rows and the keyword beating them. Row fixes act on the **ticked** rows (all ticked to begin with).
  - A finding carries a stable `key` and a `fingerprint` of its evidence; **"this is fine"** stores both (`health_dismissals`), so a finding stays hidden only until its evidence changes. **Fixes are described by the server and run by the page through the same endpoints a hand edit uses** (bulk categorize, keyword edit/delete, category delete), so they get the same validation and recompute; the one new write is deleting imported 0.00 rows (`POST /api/data-health/delete-empty-rows`, this user's 0.00 rows only, snapshot first). Mounted at `/api/data-health` — `/api/health` is the liveness probe. The Home attention strip speaks only for *high* findings; the tile carries the open count.
- **Graphs** — Comprehensive graphs on expenses, categories/types, and timeline. The overview puts its filters in a **sticky left rail** (period presets, dates, account, holder, business, currency toggle, hidden categories and the leave-out chips, whose list scrolls at `max-h-[38vh]` so the rail never outgrows the window), with the charts in a **two-column grid from 1280px**. Width does not go into wider charts: a 260px-tall chart stretched to 1700px flattens every shape in it, so the page spends the window on more charts at once and keeps each near its natural proportion. Amounts aggregate in a single display currency (FX-converted) with a toggle back to original currency (see Decisions). Specific charts to be refined later.
  - **Leave out** (both graph pages) — a row of category chips; clicking one drops that category from every total, chart and list on the page ("costs without Company, without Travel"). It *subtracts* (`?excludeCategoryIds=`, AND-combined) where the category filters elsewhere *select*, so it narrows a selection rather than widening it, and uncategorized rows survive it exactly as they survive hiding. Hidden categories are not offered — they are already out.
  - **Explore** (`/graphs/explore`, a tab beside the overview) — the drill-down half of Graphs: a **year row with its twelve months, each a toggle**, so a period is a *set* of months rather than a range (a date range sits underneath for what the toggles cannot say; the two AND). The left column charts the categories of the selected period, the right column lists the transactions behind them, ordered by **value or date** (or description). **Expenses and income are independent toggles**: with both on the column draws a ring for each (out and in, sharing one colour ranking) and the net beneath them. A **year range** picks which year rows the month grid draws — display only, never what is counted — defaulting to the most recent three with data. Clicking a category drills the ring into its subcategories and narrows the list; picking a subcategory narrows only the list, so the ring keeps its share readable. Rows are **recategorized inline** exactly as on the transaction list (click the category, pick or create another) — the list is where a miscategorization shows itself, so it is where it gets fixed; the row leaves the view if it no longer belongs to it, and the ring refreshes with it. **Layout:** the month grid is a band across the top with the selected period's totals (spend, received, net, transaction count, unconverted note) beside it rather than under the ring — they describe the period, not the categories — and below it the ring and the list sit side by side, the list using the same ledger row as the transaction page (date · description · account above 1280px · category · amount).

## Decisions (locked)

Non-obvious calls agreed during requirements refinement:

- **Expense/income is derived, not stored.** The canonical field is a single **signed `amount`**. `amount < 0` = expense, `amount > 0` = income, computed at query time. No `category_type` on categories. Refunds naturally net against spend. (The `category_type` / `Transfer` fields in the seed JSON are treated as sample noise, not schema.)
- **Business vs. personal lives on the transaction/split**, defaulted from the category. Mechanisms: (1) a `business | personal | mixed` flag per transaction and per split line; (2) a per-category default that auto-tags new transactions; (3) a bulk "mark whole category as business" action (e.g. ZUS). Filtering stays a single indexed column.
- **One amount, one currency per transaction.** When a CSV offers two amount/currency pairs (e.g. Alior operation-currency vs. account-currency), the template maps the account-currency amount as canonical and keeps the foreign amount+currency as optional metadata for the FX toggle.
- **Cash = one LIFO pool per currency.** ATM withdrawals add to the pool; virtual cash spends draw it down last-in-first-out. Reports show the _net_ withdrawn (withdrawal minus matched spends) with drill-down into the matched spends. A pool may go **negative** (spends exceed recorded withdrawals) — allowed, not blocked.
- **Cash-pool feeding:** categories have a boolean `is_cash_withdrawal`; a seeded "Cash Withdrawal" category ships with it set. Any transaction landing in a flagged category feeds the pool of its currency.
- **LIFO edge semantics:** a cash spend draws from the most recent withdrawal _on or before_ the spend date; if its remainder is insufficient, the spend splits across the next-most-recent withdrawals; if the pool is exhausted, it goes negative.
- **Classification mechanism.** Lowercase + strip diacritics, tokenize the description; for a keyword of N words, slide an N-token window and match each token within the distance threshold (so `żabka`→`zabka`→`zapka` match at distance ≤1). Substring-containment semantics with fuzzy tolerance. Threshold = global user setting, overridable per keyword. Manual categorizations are locked; longest keyword wins ties.
- **Rule changes trigger a full recompute.** Adding/editing/deleting a keyword re-runs the engine over all **non-locked** transactions — a new longer keyword may re-win transactions from a shorter one; deleting a keyword reverts its transactions to uncategorized (unless another keyword matches). Engine-assigned state is always a pure function of (rules, transactions, locks).
- **FX conversion fallback chain:** (1) use the effective rate from the CSV when both amount pairs are present (rate is derivable per row); (2) else a user-uploaded rate table; (3) else a daily-rate API (ECB/NBP) as last resort, since bulk API history is unreliable. Rates keyed by `(date, from, to)` and cached. Graphs toggle original ↔ converted; the conversion target is the user's default currency. If no rate is found at any level, the transaction is shown unconverted and visibly flagged (never silently guessed).
- **OFX dedup = `FITID` first.** OFX carries a bank-assigned unique transaction id; when present it *is* the dedup key (stored `fitid:`-prefixed so the two key spaces can never collide), otherwise the standard `date|description|amount` key applies. Dedup stays per account and occurrence-counted, so two `STMTTRN`s sharing a FITID in one file are still two transactions. Known trade-off: the same statement imported once as CSV and once as OFX will **not** dedup against itself.
- **OFX description = `NAME` + `MEMO`**, joined by a space, skipping any field that merely repeats text already collected (banks routinely copy NAME into MEMO). The fields and their join order are configurable per account (`NAME`, `MEMO`, `PAYEE.NAME`, `CHECKNUM`, `TRNTYPE`) — optional; an account with nothing saved imports on the defaults.
- **OFX account identity: warn, never block.** The first OFX imported into an account records its `BANKID`/`ACCTID`; a later file with a different one shows a preview warning and imports anyway (banks do change identifier formats, and the user picked the target account deliberately). A "forget account id" action clears it.
- **OFX dates and currency.** `DTPOSTED` is truncated to the date *as written* — the bracketed timezone is parsed but not applied, so a transaction lands on the day the bank shows. `CURRENCY` means the amount itself is in that currency; `ORIGCURRENCY` + `CURRATE` means the amount is in `CURDEF` and the original is recorded as foreign amount/currency, which hands the FX chain a per-row derived rate. OFX's sign convention (negative = outflow) already matches every CSV template.
- **CSV template model (per account):** delimiter, decimal separator, encoding, **skip-rows / header-row index** (Alior has a criteria line _before_ the header), date format, chosen date column, N description columns to merge, N amount columns to sum (empty cells count as 0), currency column (else account currency), and row-filter rules. Datetime values are truncated to date — the transaction stores a date only. Templates are copyable between accounts. Real samples in `@samples` are intentionally diverse: Alior (`;`-delimited, comma decimal, Polish/non-UTF-8 encoding, `DD-MM-YYYY`, two amount+currency pairs), Revolut (`,`, dot decimal, UTF-8, `Amount`+`Fee`, `State` filter), Itaú (`,`, dot decimal, single amount, implicit currency). Sign convention across all: **negative = outflow**.
- **A CSV line an unquoted delimiter shifted is flagged, never guessed.** Alior prints some sender names with a bare `;` (`IXE LLES;BE`), which moves every later column by one. A line whose non-empty cells run past the header is an error in the preview; a money cell may carry a currency code or symbol but not words or slashes (it used to parse prose as its digits run together); a currency cell must be a three-letter code.
- **A line whose amount cells are all empty is an error, not 0.00.** ING prints card holds ("Blokada") with only a hold amount; they used to import as 0.00 transactions. A cell holding `0,00` is still a real zero.
- **Upload rollback:** an upload in the archive can be deleted, removing its imported transactions — with a warning listing how many locked (manually categorized) or split transactions would be destroyed.
- **Imported transactions are immutable** in date/description/amount (they must stay dedup-stable); only category, business flag, hashtags, and splits are editable. Manual transactions are fully editable.
- **Export/import formats:** categories as JSON (round-trips the seed shape); keywords as CSV (`keyword,category,subcategory,distance`) for easy spreadsheet editing.
- **Graphs v1 shortlist:** monthly income vs. expenses bars; stacked monthly expenses by category; category breakdown donut/treemap for a selected period with subcategory drill-down; single-category timeline; business vs. personal split over time; spend-per-hashtag totals. All respect hidden categories and the FX toggle.
- **Auth:** session-cookie login with bcrypt-hashed passwords. No email/password-reset flow — an **admin** resets passwords in-app, or a CLI script (`server/scripts/reset-password.js`) resets any user from the command line. Accounts are admin-created (no self-registration); a default `admin`/`admin` is seeded on first boot.
- **UI conventions.** The pages were reworked page by page to use a desktop window; these are the idioms they now share, and a new page should follow them rather than invent its own.
  - **Page width is per route, set in the shell.** `AppShell` maps the route to one of three caps — `narrow` (`max-w-2xl`) for single-column forms, `mid` (`max-w-4xl`) for mixed prose/controls, `wide` (`max-w-[110rem]`) for tables, ledgers, boards and graph grids — and the header and warning banner follow the same cap so the nav stays aligned with the page under it. One global `max-w-5xl` had wasted most of a desktop screen and silently capped the pages that asked for more.
  - **A sticky left rail holds what narrows the page**, the rest of the window holds the work: filters on Transactions and the Graphs overview, the period on Explore, the account and file on Uploads, the sections on Settings. A rail caps its own scrolling list (`max-h-…`) so it never outgrows the window — a sticky rail you have to scroll to reach is not one.
  - **A record is a ledger row**: one line, grid-aligned columns, the description (or name) the only elastic track, actions right. Used by Accounts, Transactions, Explore's list and the keyword table. A `display:none` cell still holds its grid track, so a column that disappears at a breakpoint needs the *template* to change with it, not just the cell.
  - **A drill-down drawer where the page needs its width.** Keywords opens its panel as a column beside the table; the Budget statement cannot spare the width (a column per month), and a panel that wraps below the table opens out of sight — so Budget's panel is a drawer fixed to the right edge, over the table.
  - **Where records are few and their shape matters, a board of cards** instead: Categories, the Home tiles, the account boxes on Uploads.
  - **Width goes to more content, never to wider charts.** A 260px-tall chart stretched across 1700px flattens every shape in it.
  - **Counts live next to the thing they describe** — a category's transactions, a rule's matches, an account's date span. Every such figure skips split containers (a split counts once, through its children) and is FX-converted before it is summed when it is money.
  - **An endpoint other pages read for names keeps its counts opt-in** (`/accounts?stats=1`), so filling a dropdown never pays for a scan of the transactions table.
  - **View preferences live in `localStorage`; data preferences live in user settings.** Which columns the transaction list shows is a view preference (`bext.transactions.columns`); the page size, which changes what is fetched, is a setting.
  - **The router lives in `location.hash`**, so in-page navigation must scroll elements — an `href="#id"` anchor navigates the app away from the page. Smooth scrolling is not guaranteed: some environments ignore `behavior: 'smooth'` outright rather than jumping, so a jump-to-section checks a few frames later and falls back, and honours `prefers-reduced-motion`.
  - **Per-category colour is used wherever a category appears** (see the colour decision below), including the bars on Categories and Keywords.
- **Categories carry a colour, derived and not stored.** `client/src/lib/categoryColors.js` maps a category to one of 16 hand-stepped hues (a light and a dark list, as in the chart palette) by `id * 7 % 16`, and `CategoryIcon` tints its glyph with it — or draws a swatch in it when the category has no icon, so a category always carries its colour. A subcategory takes its parent's hue. The stride spreads consecutive ids around the hue wheel; seeded categories have consecutive ids, and a plain `id % 16` gave neighbouring categories neighbouring hues. Deriving from a sorted position would repaint every later category when one is deleted, which defeats a colour you have learned. Colour is redundant coding — the name is always beside it. **This is deliberately not the chart palette** in `charts.js`, which colours by a category's rank *within one chart* (8 slots, tail folded into "Other") and so cannot be stable per category; the two therefore disagree, and unifying them would mean giving the charts stable per-entity colour.
- **The AI proposes rules, the keyword engine still owns classification.** An accepted proposal becomes an ordinary keyword, so everything downstream — longest keyword wins, locks, the full recompute, deleting the rule to undo it — behaves exactly as a hand-written rule does. Nothing in the AI path writes a category the engine could not have written itself, which is why an AI run needs no new rules about re-running or conflicts.
- **The AI log is kept on a rejection, not deleted.** The log is what stops an engine paying to reach the same answer you already turned down; deleting a rejected proposal would make the next run buy it again.
- **Which Budget line a row lands on** — first match wins: (1) a **pin** on the transaction; (2) a **routed hashtag** (lowest `budgetOrder` when it carries two); (3) its subcategory's line; (4) its category's line; (5) a hidden category nobody mapped → a synthetic *hidden* excluded line; (6) otherwise **Unassigned** — uncategorized money and categories not yet placed — which counts in the normal month, visibly, because the columns must add up to what really left the accounts. **The mapping ignores `isHidden`**: a hidden category mapped to a line (cash parked under Transfers) counts there, while every other page keeps hiding it.
- **Spreading changes when, not where.** A spread row lands on whatever line the rules give it and is cut into N equal monthly slices from the month it was paid, the rounding remainder on the first slice; slices of a purchase made before the window still count inside it. Conversion happens on the whole amount, then it is sliced.
- **Budget config lives on the entities it describes**: `budget_line_id` on categories, subcategories, hashtags (plus `budget_order`) and transactions (the pin, beside `spread_months`), all `ON DELETE SET NULL` — deleting a line sends its rows to the next rule. No targets in v1: the page describes actuals; budgets to aim at come once the numbers are trusted.
- **Money is stored as integer minor units** (`amount_cents`) — never floats. Dates are `TEXT 'YYYY-MM-DD'`.
- **Seed mapping:** `Company` seeds with `businessDefault=true` (all its subs are business_cost); `Transfer In/Out` seeds hidden; a dedicated `Cash Withdrawal` category (`is_cash_withdrawal=true`) is appended at seed time. The seed's `category_type` is ignored.

## Development

- `./dev.sh` starts both halves at once (installing deps on first run) and tags each log line `[server]` / `[client]`; Ctrl-C stops the pair, and if either dies the other is shut down too. Or run the two by hand:
- `server/`: `npm run dev` (port 3001), `npm test`, `npm run db:generate` (Drizzle migration from `src/db/schema.js`), `npm run db:backup [label]` / `npm run db:restore <file>`. Migrations auto-apply on boot; DB file at `server/data/bext.db` (gitignored), overridable with `BEXT_DB_PATH`.
- `client/`: `npm run dev` (Vite, proxies `/api` → 3001; `BEXT_API_URL` overrides that target), `npm run build`. `$lib` alias configured for shadcn-svelte compatibility.
- Production mode: after `client` `npm run build`, the Express server serves `client/dist` itself — one process on :3001.
- No workspace tooling — `npm install` separately in each folder.
- **Secrets live in `server/.env`** (gitignored; `server/.env.example` lists them), read on boot when the file exists — a real environment variable always wins over it. `BEXT_AI_KEY_SECRET` encrypts the stored provider keys (rotating it means "enter your key again", never a crash) and `BEXT_GEMINI_FREE_KEY` offers the free Gemini engine (unset = not offered). Note `server/data/.ai-key` is *not* a place for a provider API key: it is the generated fallback for `BEXT_AI_KEY_SECRET`. Either source accepts 64 hex characters or any passphrase, and tolerates a pasted `NAME=value` line, because a hand-edited value must not turn "save my API key" into a 500. Provider calls are stubbed in tests by replacing `PROVIDERS.<id>.complete` — `npm test` never reaches a network or spends a key.
- **Trying the UI without touching your database.** `server/data/bext.db` holds real data, and the dev stack on :3001/:5173 may already be running against it. To exercise a page against realistic data, run a second instance on its own ports and its own file: `PORT=3002 BEXT_DB_PATH=/tmp/demo.db BEXT_BACKUP_DIR=/tmp/backups node src/index.js` in `server/`, and `BEXT_API_URL=http://127.0.0.1:3002 npx vite --port 5174 --host 127.0.0.1` in `client/`. Use `127.0.0.1` rather than `localhost` for the demo: cookies ignore ports, so a `localhost` session cookie would collide with the real app's. The throwaway database seeds `admin`/`admin` on first boot.
- Fuzzy-match guard: tokens shorter than 5 characters always require an exact match regardless of the distance setting (prevents "zus"≈"bus").

## Stack

- **Frontend:** Svelte (plain, not SvelteKit) + Vite + Tailwind + shadcn-svelte
- **Backend:** Node + Express
- **Database:** SQLite via Drizzle ORM
- **Language:** JavaScript (not TypeScript)
- **Testing:** Vitest
- **AI:** `@anthropic-ai/sdk` for Claude; OpenAI, Gemini and DeepSeek over their HTTP APIs (no extra SDKs)
- **Layout:** monorepo with `client/` and `server/` folders, no workspace tooling

## What is deferred

- ML-based *automatic* classification. The engine stays keyword substring matching with fuzzy tolerance; the LLM proposes rules for a human to accept (see AI categorization) rather than categorizing rows on its own.
- OFX investment statements (`INVSTMTRS`) — the buy/sell/units model does not fit a single signed amount; such a file is rejected with a clear message.
- Auto-reconciliation of internal-transfer pairs (transfers are only _hidden_ for now).

## Defaults

- Seed categories from `@samples/category_seed.json`.

## Samples

- `@samples` holds **synthetic** extracts in the exact shapes of real ones — invented merchants, people, accounts and amounts, so the repository carries no one's bank data: `Alior.csv` (Windows-1250, CRLF, criteria line before the header, `;`, comma decimals, two amount/currency pairs), `Revolut_sample.csv` (`Amount`+`Fee`, `State`, datetimes), `itau_combined.csv` (single amount, implicit BRL, `SALDO` noise rows), `itau_extrato_sample.ofx` (OFX 1.0.2 SGML, MEMO-only descriptions), and `bext-fx-rates.csv` (a public EUR/PLN daily rate table). Real extracts go in `samples/private/`, which git ignores — never commit a real file.
- `@samples/category_seed.json` is what a new user starts with, in the shape the Categories page exports (`GET /api/categories/export`) — so an export can become the seed. It is a **curated** tree: categories, subcategories and keywords for businesses anyone can use; keywords naming people, addresses, employers, schools, doctors or account numbers are not shared. `@samples/keywords.csv` holds the same keywords in the Keywords page's import format (`keyword,category,subcategory,distance`), for adding them to an existing user. Synthetic OFX fixtures covering the XML 2.x dialect, credit cards, `ORIGCURRENCY` and the error paths live in `server/test/fixtures/`. The CSVs are intentionally diverse — see the CSV template model in Decisions.
